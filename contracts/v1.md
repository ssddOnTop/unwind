# Local Companion contract v1 — frozen

Frozen 2026-11-14 after reading the current PLAN.md and research/health-evidence.md, ios-feasibility.md, orchestration.md and data-sources.md. This is the builder integration boundary, not clinical validation. The user's explicit no-auth decision overrides older research/plan language about authenticated ingestion. Ownership is contracts/ only.

## Transport and exact types

Native SwiftUI iOS 17+; default base URL `http://127.0.0.1:8000`. Python service binds loopback only. No authentication, user IDs, tokens, public deployment, wildcard CORS, accounts, email sending or external enrollment. Simulator-to-Mac is the initial topology; a physical device's loopback is that device, not the Mac. Device networking requires a separately approved boundary. HealthKit is a read-only optional adapter after explicit permission; toolchain/device verification remains blocked, not claimed working.

JSON, UTF-8, snake_case properties, case-sensitive string IDs, integers for steps/revisions, booleans for switches. Swift can use explicit CodingKeys; dates remain strings. Every property in the relevant schema object is required; nullable properties must be explicit null, not omitted. Unknown properties are rejected. No arbitrary dictionaries, raw provider payloads, raw samples, receipts, email bodies, bank identifiers, secrets or private descriptions. Normalized live daily counts are sensitive too; do not log them. Notes are optional in meaning but encoded as an empty string when absent, max 1000 characters; do not put private records in notes.

`state.schema.json` is Draft 2020-12. Its root validates GET /state. Its `$defs` are the **normative exact property names, required fields, enums, nullability and shapes for every endpoint**. Use the referenced definition plus the same `$defs` to validate another payload. Enable format validation. Semantic rules below are additional mandatory checks, not all expressible in JSON Schema. No pagination or incremental cursor in v1: revision is the full-snapshot cursor; clients fetch the whole state.

## Eight routes, no more domain routes

All successful responses are HTTP 200, including idempotent retries and synchronous processing. No 202/jobs route. Automatic framework-generated GET /docs and GET /openapi.json are additional documentation routes; disable alternate documentation routes if generated by default. Generate OpenAPI from typed handlers, including the common errors; never maintain a separate handwritten Swagger document.

| Method/path | Exact request definition | Exact success definition |
|---|---|---|
| GET /health | No body/query | health |
| GET /state | No body/query | state |
| POST /observations | observation_batch | ingestion_response |
| POST /feedback | feedback_request | state |
| PUT /preferences | preferences_request | state |
| POST /process | process_request | state |
| POST /demo | demo_request | state |
| DELETE /data | delete_request (JSON body) | state |

Health example: `{"schema_version":"1","status":"ok","service":"local-companion","capabilities":[{"id":"persistence","version":"1","status":"available"}]}`. Return all installed/known capability entries, not just this abbreviated example. Health is degraded only when a required local capability fails; absent optional providers are reported as not_configured, not a health failure.

All mutation requests begin with `schema_version:"1", request_id:string, data_epoch:string`. Obtain the epoch from state first; the example epoch is illustrative, not hard-coded by clients. Remaining exact request fields:

- **Observations:** `observations:[observation], source_updates:[source_update]`; see the complete observation-batch example. Arrays may be empty, up to 500 observations and 2 distinct source updates, total body limit 1 MiB. Reply `{"schema_version":"1","accepted":N,"ignored":M,"state":<State>}`. Counts count submitted observation revisions only; accepted + ignored equals batch length. Source updates do not contribute to counts.
- **Feedback:** `card_id`, `kind`, `value`, `scope`, `event_ref`, `attribution`, `note`. For example correctness of a purchase attribution: `{"schema_version":"1","request_id":"feedback-1","data_epoch":"demo-epoch-1","card_id":"purchase_recurrence","kind":"correctness","value":"partial","scope":"event","event_ref":{"observation_id":"demo-purchase-1","revision":1},"attribution":"shared","note":"Synthetic shared purchase correction."}`.
- **Preferences:** `preferences:<complete Preferences>`; replacement, not patch. The complete shape appears in state.example.json and `$defs.preferences`. No extra revision wrapper. Serialized writes use last committed replacement; clients refresh before editing and must not blindly retry a stale edited form under a new request ID.
- **Process:** `synthesis_mode:"disabled"|"scripted"|"live"`. No caller-provided clock, provider name, prompt, model settings or arbitrary tools.
- **Demo:** `action:"seed"|"reset", fixture_set:"representative-v1", consent_demo:true`. Explicit action is consent for synthetic demo only, never permission to query a real source or use cloud AI.
- **Delete:** `confirm:"delete_all"`. Deletes all application data, not just visible cards. No selective deletion or source-admin route in v1.

## State, revision and retry semantics

State is a complete bounded snapshot: schema_version, data_epoch, revision, generated_at, evaluation_date, preferences, sources, observations, ledger, feedback, notification_intents, process, limitations. Collections are always arrays; order sources as demo/healthkit/plaid/email, ledger as purchase_recurrence/recorded_steps/preference_filter, observations by ID then revision, feedback by created_at then ID, intents by scheduled_at then ID. Fixture arrays use this same ordering. Use schema property names, not display labels, as identifiers.

`revision` is a monotonically increasing committed snapshot counter within an epoch. Reads never mutate it. `generated_at` is snapshot commit time, not GET request time. No-op ingestion and identical request retries do not bump it. `process.input_state_revision` identifies the evidence/context snapshot consumed, not necessarily the resulting state revision. Each card has a stable ID equal to its scenario_id; change card revision only when its semantic content changes. Preserve stable suggestion IDs from scenarios.json. Evidence references always identify an exact observation ID/revision present in observations; feedback is separately linked. All three cards may remain present in empty state with insufficient_evidence status for purchase/steps; preference card reports current explicit settings.

Serialize mutations and commit accepted evidence, feedback/preferences, deterministic recomputation and notification cancellations atomically. Deterministic ledger updates happen on ingestion/feedback/preferences, not only on /process. Capture a snapshot for optional synthesis; do not hold a DB lock during model calls. Recheck epoch, source consent and context before publishing drafts. GET /state can show running process status. A concurrent /process returns 409 busy; no second model run. Recover a persisted running job on restart as failed/interrupted work (reason internal_error), retaining a queryable ledger; retries are explicit and bounded.

Idempotency is keyed by `(data_epoch, route, request_id)` and canonical JSON body (sorted keys, insignificant whitespace ignored). Identical retry returns the original response including counts; changed body with same key is 409 idempotency_conflict. Check cached successful replay before current-epoch rejection. Retain receipts within the epoch for 90 days. After that, clients must refresh/reconcile rather than blindly retry; observation identity still prevents duplicates. New request with old epoch returns 409 epoch_mismatch and performs no write. Do not automatically retag an offline queue to a new epoch. iOS discards pending uploads/feedback on deletion/reset and cancels all old notifications.

## Observations and append-only evidence

Observation identity is a client-generated opaque stable ID scoped to an epoch, source and mode; do not embed raw bank/account identifiers. `(id, revision)` is unique. First revision is 1. Same revision and identical content is ignored; same revision with changed content is 409 revision_conflict. Older unseen revision is ignored. A newer revision must be exactly latest+1 and reference that latest revision in supersedes; gaps/conflicting identity or links are 409 revision_conflict. Duplicate entries within one batch follow these same rules in submitted order; conflicting duplicates reject the entire batch. Batch validation is atomic (no partial acceptance on an error).

For new posted IDs replacing pending IDs, revision=1 may supersede the exact pending reference. Resolve references against stored evidence plus the whole batch independent of array order. Require same source/mode/kind, acyclic links and a single active successor; do not invent a link using merchant/date similarity. Stable existing IDs retain kind/source/mode. Exclude superseded records, pending records, tombstones and refunds from current purchase counting. `operation:"remove"` is a new revision with lifecycle removed and both purchase/activity null; preserve identity/time/provenance and exact supersedes. Old revisions remain evidence, except privacy deletion/retention erasure.

Purchase upserts have purchase object and null activity; category is restaurant/grocery/other/null and merchant is nullable. No price is needed in this modest v1. `local_date` is authorized_date when known, otherwise posted_date; one must be known and match. Posting date is never called meal time. Pending records may have null posted_date. Datetime precision requires a genuine offset-bearing timestamp whose date in observation.timezone equals local_date; date precision requires occurred_at=null. Do not manufacture midnight or a consumption timestamp. Unknown source dates cannot enter v1 and must be held by the adapter, not guessed.

Activity upserts have activity object and null purchase, lifecycle recorded, metric steps, nonnegative integer value, unit count. One authoritative aggregate per source/local_date/timezone, stable ID across daily revisions. Export HealthKit's reconciled daily cumulative aggregate, not parallel phone/watch samples or summed overlapping sources. Empty query means no observation, never an inserted zero; an explicit zero is a recorded value, still not inactivity. The fixture aggregate uses demo_fixture/synthetic. Live HealthKit uses healthkit_daily_steps/daily_cumulative_sum. Plaid uses plaid_transactions/provider_record only after a future approved live connection; currently reject its ingestion as not_configured. Live mode is permitted only for HealthKit in this v1; demo always fixture. Never combine fixture and live evidence in one card: when healthkit is enabled and app-consented, the steps card selects healthkit even when empty; otherwise it uses demo. Purchase card uses demo only. Exclude disconnected/revoked sources immediately.

Household attribution self/shared/other/unknown is a claim about the transaction context, never consumption. User feedback changes effective attribution in a separate correction overlay. Unknown/shared/other records may remain in observed purchase totals, but only self-attributed qualifying records can establish personal-suggestion eligibility. Incorrect event feedback excludes that event from eligibility; partial with explicit attribution applies that attribution. Never overwrite immutable original evidence.

Default observation retention is 90 local days, based on supplied local_date. Remove older observation contents, affected evidence-linked feedback and derived drafts/checkpoints, and recompute cards so references do not dangle. Older incoming observations are rejected invalid_request rather than silently counted; no-op ingestion cannot extend retention. No raw private content is stored at any point. Timed retention is product housekeeping, not a clinical window.

## Consent and sources

Exactly four source records: demo, healthkit, plaid, email. `enabled` mirrors preferences.enabled_source_ids but does not imply capability or device permission. Capability available means adapter boundary is supported, not proof of device testing. Plaid/email are not_configured; do not simulate live email or fabricate bank keys. Enabling either returns 409 not_configured without changing state.

Fresh defaults: enabled_source_ids=[demo], but demo consent=not_requested and no records. Consent becomes granted only through explicit demo action or explicit preferences save retaining/adding demo. HealthKit starts disabled/not_requested; explicit addition to enabled_source_ids is app consent to normalized local-backend sync, not Apple read permission. Removing a source sets consent revoked, stops collection/use, removes pending source-derived intents/drafts immediately and leaves previously ingested evidence visible as historical until retention or DELETE /data. Re-adding requires explicit save and never infers permission from old records. No silent initial live collection.

Observation source_updates report query outcomes, not permission grants; cannot enable a source or set consent. Reject uploads/source updates without enabled + granted app consent (409 consent_required). For HealthKit, authorization_requested means the permission UI was requested; read_access stays unknown for empty/failed queries. samples_readable only reports actual readable results, not global permission. Empty sensor coverage is unknown. Successful samples only support partial/unknown coverage, never continuous wear. Report last_attempt_at on any attempt; last_success_at on success or empty; an error preserves previous success. Empty updates set status empty and coverage unknown. Error uses protected_data/unavailable/query_failed without raw error data. Successful update has error_code null. Readable success still cannot assert full coverage. Error/empty read_access must be unknown for HealthKit. source_update attempts must not go backwards; older reports are ignored. Derive stale when last success precedes the previous local date at evaluation; do not infer behavioral change from freshness.

Timezone must be a valid IANA zone. Dates remain explicit local dates; preference timezone controls evaluation windows and notification scheduling. Existing date-only records retain their original date/zone; timezone changes never rewrite them. Exclude records whose timezone differs from current preferences from aggregates, with a visible limitation, until the adapter provides correctly reaggregated new revisions. Use true timestamps for rebucketing only through an adapter revision, never silently during presentation.

## Preferences, feedback and immediate filtering

Fresh defaults: food_suggestions=true, activity_suggestions=true, suppressed_scenario_ids=[], enabled_source_ids=[demo], timezone=America/New_York, notifications={enabled:false,local_time:"18:00"}, all three constraint booleans=false, notes="", cloud_consent=false. The example intentionally demonstrates non-default constraints. Persist complete preferences independently from synthesis. notes is explicit context only; no automatic free-text extraction into medical rules. Unstructured recurring-context inference and expiring preferences are deferred; enduring flags and scoped event feedback cover v1.

Correctness accepts correct/incorrect/partial, usefulness accepts useful/not_useful/partial, suppress accepts stop only. Valid scopes: correctness card or event; usefulness card; suppress card or scenario. event scope requires event_ref belonging to the referenced card; other scopes require event_ref=null. attribution is permitted only for correctness/event on a purchase. Correctness/card does not erase source evidence; incorrect/partial flags disputed interpretation and suppresses its suggestion pending a later explicit correct verdict. Event corrections use latest committed feedback for that event; explicit correct clears a prior exclusion. Usefulness never changes evidence correctness. not_useful/partial marks the current card suggestion unavailable until a later useful verdict; no automatic replacement or repeated prompt.

Feedback IDs are server-generated stable opaque IDs (request_id may be reused as the feedback ID within the epoch). created_at is server time. Preserve prior feedback as an audit trail. Card references must exist (404 not_found). Exact event references must resolve (404 not_found). Suppress is durable: scenario scope adds scenario_id to suppressed_scenario_ids; card scope persistently suppresses that stable card's suggestion. In v1 IDs are one-to-one, so both scopes have the same effective stop behavior and update that preference list. Explicitly removing the scenario from a later preferences replacement is the only unsuppress operation; historical feedback does not reapply a cleared stop.

food_suggestions=false blocks food candidates; activity_suggestions=false or movement_restriction=true blocks movement candidates. no_kitchen/no_spending block candidates requiring those resources, not all food-related language. The planning candidate requires neither a new purchase nor kitchen access; it plans an already intended purchase. Filter immediately on all writes and again before notifications/model publication. Keep recorded facts visible; suppressed cards/candidates must not generate intents. No compatible suggestion means abstain, not an alternative treatment.

## Deterministic ledger and notifications

scenarios.json is the authoritative operational setting set, rule version 1.0.0. These are arbitrary transparent product rules, **not clinical thresholds**. Purchase display window includes evaluation date D and previous 27 dates. Recurrence requires >=3 distinct qualifying dates AND latest-earliest >=14 calendar days (the precise interpretation of spanning >=2 weeks; merely crossing ISO week boundaries is insufficient). Display dates/counts; do not label diet, calories, portions, obesity, diagnosis, risk or future weight. Shared/unknown corrections may remove personal eligibility without removing the observed household fact.

Steps summarize D-7 through D-1 inclusive, seven completed local dates; sum selected current daily values, count distinct dates with records, never zero-fill or extrapolate. If empty, recorded_steps=null (not 0), days_with_records=0, status=insufficient_evidence, coverage=unknown, suggestion=null and use the exact empty wording in scenarios.json. With records, observed totals are permitted despite gaps, with limitations. Do not compare step counts to intensity guidelines or claim inactivity. preference_filter has an evaluation-day window, no evidence requirement and never emits a notification.

observed is a direct description; inferred is nullable and only permitted for the transparent product recurrence interpretation, never a model conclusion. Card evidence includes the exact active revisions used in displayed totals; feedback_ids identifies corrections relevant to eligibility. Limitations explain missing sources, coverage, conflicting attribution and dates. Any card with no usable evidence remains unknown/insufficient, never healthy/unhealthy.

Notification intents are a complete desired pending set, not evidence of delivery. Defaults emit none. When enabled, choose at most one eligible candidate per evaluation local date, purchase before activity, at the user's local_time strictly in the future that date; if already passed, skip that day. Expire at next local midnight. Skip nonexistent DST times; choose first occurrence of repeated times. Intent ID is stable `scenario_id:YYYY-MM-DD` within an epoch. Store issuance before returning it; same suggestion cannot issue again until >=7 local dates later, even if no delivery acknowledgment exists. Reprocessing must not regenerate a cancelled/suppressed intent for that date. No delivery/ack route in v1. iOS upserts by intent ID and cancels any previously scheduled ID absent from the current set, and requests OS notification permission separately. Generic title/body are fixed in the schema. A denied OS permission never becomes evidence of refusal or correctness. Reset/delete clears all issued/pending IDs and client requests. No scenario notification in synthetic mode is scheduled by default.

## Process and replaceable backend extensions

Core owns only registry lookup and dispatch by capability ID/interface version. HTTP composition/startup, storage, scenarios, feedback, provider adapters, scheduling and synthesis are replaceable independently; core contains no SQL, health rules or SDK prompts. Capability IDs: persistence, scenarios, feedback, demo, healthkit, plaid, email, synthesis; interface version "1". Registry metadata returns availability; duplicate capability/version registration fails at startup. Missing optional synthesis does not prevent state/ledger. Replacement extensions must consume/return these typed domain objects, honor the same transaction/epoch boundaries, and pass the same fixture/schema tests. Do not import another extension's internals.

/process runs deterministic evaluation first, then optional synthesis synchronously, bounded to 30 seconds. Disabled yields skipped/disabled. Live checks credentials first (absent => skipped/no_credentials); then cloud_consent (false => skipped/cloud_consent_required). Even true consent does not authorize live HealthKit transmission in v1: return skipped/live_not_approved if live health evidence is present. Live fixture-only synthesis requires an explicitly configured provider; no hidden default provider or external tools. No error in synthesis can erase/replace ledger or prevent a successful deterministic process response; record failed/timeout or failed/invalid_output as appropriate. Entire process is completed when ledger completed and synthesis reached completed/skipped/failed. Ledger failure makes process failed.

Scripted mode must execute the **actual Deep Agents SDK graph with an explicit scripted model/test double**, exclusively on synthetic evidence, without network or keys; never call it live AI. Reject scripted mode with any live evidence (409 invalid_request). Return labelled scripted drafts with valid card/evidence refs. Deep Agents can produce optional wording/coverage drafts only; it cannot mutate observations, ledger, preferences, feedback or notification intents. No shell, external search, raw record tools or autonomous memory writes. Interface settings bound 4 model calls, 4 tool calls, 8000 input and 1000 output tokens across subagents. Missing SDK means unavailable synthesis, not a fabricated successful scripted run. SDK persistence/checkpoints are separate from authoritative domain state and deleted with it. Invalid/dangling/stale drafts are discarded. Daily worker is optional outside core and must obey these same idempotency/cooldown rules; no exact iOS daily wakeup promise.

## Demo, deletion and errors

Seed only into an empty instance or an unchanged representative-v1 fixture instance. Seed into an existing compatible demo is a no-op and does not overwrite user preferences or feedback; if demo observations are incomplete/modified, or any non-demo evidence/source consent exists, return 409 demo_conflict. Initial successful seed grants demo consent, applies representative fixture preferences, observations and fixed test clock from scenarios.json, and returns the example-equivalent state (server-generated IDs/commit revision may differ). The sample batch is replayable after seed: all six records ignored. To test accepted ingestion, use an empty epoch, explicitly consent demo with PUT preferences, replace the example epoch, then upload the batch.

Reset is **demo-only**, never a disguised live-data deletion. Reject reset if any live observation/history, live app consent, or non-demo source is enabled. On a permitted reset, atomically erase prior demo records, feedback, preferences, jobs, checkpoints and intents, rotate data_epoch and install the exact representative fixture. Retry the same reset request returns the same new state, not another reset. New reset request with the old epoch fails epoch_mismatch. The fixed demo clock remains active while in the representative fixture session; no client clock input. DELETE /data exits demo clock mode.

DELETE /data cancels in-flight jobs and erases evidence, revisions, feedback, preferences, ledger projections, drafts, SDK checkpoints/memory and notification history, rotates epoch, then returns clean default state with idle process, empty observations/feedback/intents and insufficient-evidence cards. Source consents return not_requested. No automatic reseed. Erase idempotency caches containing prior response data; keep only the deleting/resetting request's non-sensitive body digest, old/new epoch and clean response receipt for 90 days to make that exact retry safe. No backup/trace copy may retain deleted private payloads. Old workers cannot publish into new epoch. Client clears local observations/offline queue/cache and cancels notifications on successful deletion. Local backups outside application control require separate verification; do not claim secure disk overwrite.

All errors use `$defs.error`, e.g. `{"error":{"code":"epoch_mismatch","message":"Refresh state before submitting new mutations.","retryable":false,"request_id":"batch-1","details":[]}}`. Return this envelope for validation and framework errors too; never stack traces/private payloads. Map 400 malformed JSON; 413 oversized body; 422 invalid_request/unsupported_version (including invalid date/unit/unknown fields/invalid feedback combination); 404 not_found; 409 revision_conflict/idempotency_conflict/epoch_mismatch/consent_required/not_configured/demo_conflict/busy; 500 internal_error. Only busy and transient internal_error set retryable=true; source/model errors belong in source/process state where the deterministic request succeeded. Reserved conflict rejection of scripted live input is 409 invalid_request. Client retries transient failure with the same request_id and body, bounded backoff; never retry consent/validation conflicts blindly.

## Builder acceptance gate

Validate state.example.json against the schema with date format checking; validate observation-batch.example.json against $defs.observation_batch. Assert evidence refs resolve, step total=13800 on 3 dates, purchase count=3 on 3 dates spanning 19 days, sources configured honestly, movement suppressed and notification set empty. Reject wrong units, date precision carrying a timestamp, wrong schema version, unknown/raw fields and kind/payload mismatches. Backend adds atomic/idempotency, pending->posted, tombstone, correction, timezone, empty coverage, revocation, cooldown, reset-live conflict, stale epoch, deletion and failing extension conformance tests. iOS consumes these fixtures without inferring absent values. JSON contract validation does not prove API implementation, iOS compilation, live provider access or clinical validity.
