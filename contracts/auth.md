# Clerk native authentication profile — frozen handoff

Status: **design contract only; not implemented**. Frozen on 2026-11-14 for native iOS + FastAPI. This additive document does not modify the current v1, experience, or Plaid contracts, schemas, routes, or generated models. Implementing this profile requires explicit backend/frontend work and matching security tests; existing anonymous behavior must not be represented as authenticated.

## 1. Authority and transport

- Clerk owns sign-in and session lifecycle. Use its default **session JWT**, not a custom user-ID claim or a custom JWT template. The built-in `sub` is the Clerk user ID; `iss` identifies its instance; `sid` identifies the session. Sources: https://clerk.com/docs/guides/sessions/session-tokens and https://clerk.com/docs/guides/sessions/manual-jwt-verification.
- Native API requests carry exactly one `Authorization: Bearer <session JWT>` header. Reject absent, duplicate, malformed, oversized (over 16 KiB), or non-Bearer credentials. No cookie fallback, query token, email, body `user_id`, `X-User-ID`, or client-selected tenant may authorize access. Never put tokens in URLs, logs, errors, receipts, outbox files, or analytics.
- Authenticate **before** opening user storage, running domain validation that consults state, consuming receipts, making vendor calls, or mutating anything. A 401 must mean the request had no domain side effects.
- Auth-profile protected routes: `GET /auth/v1/session`, `GET /state`, `POST /observations`, `POST /feedback`, `PUT /preferences`, `POST /process`, `DELETE /data`, `POST /connections/plaid` when enabled, and `GET /experience/v1` plus `POST /experience/v1/answers` when the experience profile is enabled. Future user-data routes inherit protection by default. Methods and existing mutation bodies remain unchanged; identity is not added as a client input.
- **`POST /demo` is absent (404) in the auth profile**, including for signed-in users. Disable public `/docs`, `/redoc`, and `/openapi.json` there. No public seed, debug, state, connection-status, or capability routes.
- Only `GET /health` is public: fixed liveness response `{"status":"ok"}`. It does not instantiate a user service or reveal registry capabilities, configuration, backend errors, authentication state, vendor status, or user state. This intentionally differs from the current anonymous health contract and is scoped to the new auth profile.
- Require HTTPS for deployed API traffic; retain a narrowly explicit loopback-only HTTP development/test exception. Never forward credentials across redirects or to an arbitrary endpoint. CORS and an `Origin` header are not authentication.

### 1.1. Required backend-profile and identity admission

**Security amendment:** sending a Bearer header is not proof that a server verifies it. The legacy anonymous backend can ignore that header and return its anonymous `/state`. Public `/health`, a successful TCP connection, and an ordinary state response are **not proof of auth mode**.

Choose one protected admission endpoint, **`GET /auth/v1/session`**, rather than adding owner fields to every domain response or accepting client-supplied user identity. Request: the current session Bearer JWT, no body, no identity query parameters. The handler applies the same complete verifier/pending-session policy as other protected routes, then returns only the verified principal; it does not call `service_for`, create an account mapping, open user storage, or mutate anything.

| Result | Exact contract |
|---|---|
| Verified active session | **200**, `Content-Type: application/json`, body `{"schema_version":"1","issuer":"<verified iss>","subject":"<verified sub>"}`. Exactly these three string fields; no extra properties, nulls, duplicate keys, token, email, session ID, or user data. Placeholders denote verified claim values, not literal strings. |
| Missing, invalid, or expired credentials | **401**, existing auth-profile error envelope with `code="unauthorized"`, `retryable=false`, and `WWW-Authenticate: Bearer`. |
| Verified pending session | **403**, existing auth-profile error envelope with `code="session_pending"`, `retryable=false`. |
| Verifier/configuration infrastructure unavailable | **503**, existing auth-profile error envelope with `code="auth_unavailable"`, `retryable=true`; invalid startup configuration may instead prevent startup entirely. |
| Legacy anonymous profile | Route **absent: 404**. Never implement a synthetic success, echo a requested identity, or fall back to anonymous state. |

Return `Cache-Control: no-store` and `Vary: Authorization` for success and auth failures. The client performs a fresh network request with HTTP caching disabled, accepts only an exact 200 JSON response satisfying the schema, and never follows redirects or accepts a cached/304 response. No persistent admission flag, local JWT decode, or cached handshake can substitute for this exchange.

**Client gate, before any `/state` or experience read, cached-state/answer load or display, mutation, outbox replay, or user-data background work:**

1. Capture `(configured API base URL, configured issuer, SDK user ID, SDK session ID, auth generation)` from a loaded SDK with an active session. Keep data locked. Obtain a token from that captured session and verify the context is still current before sending the handshake.
2. On return, first verify that the entire captured context is still current. Require response `schema_version == "1"`, `issuer == configured issuer`, and `subject == captured SDK user ID`, using exact equality. Do not switch a namespace to match an unexpected response. The response is server-derived evidence for this gate, **never a client-provided authorization input**. A valid token for A cannot unlock B's namespace.
3. Only after both checks succeed, mark this context admitted **in memory**, open its identity-scoped cache/client, and fetch fresh state. Every later request must still obtain its Bearer token from the same still-current session, and every response/cache write must check captured endpoint, identity, session, auth generation and applicable data epoch before use. Cancellation alone is not enough. Domain response schemas remain unchanged; do not pretend they carry an owner identity when they do not.
4. Invalidate admission before logout, account/session switch, endpoint/issuer change, a new launch/foreground re-entry, or an authentication failure. Gate data immediately; cancel/discard stale callbacks and clear visible/in-memory private data. Invalidation must permanently fence already-running callbacks, including if a later admission succeeds for the same account; use a generation/admission-attempt guard, not only a mutable admitted boolean. Re-run admission before reopening storage or replaying any work. A failed admission never opens, rewrites, or retags another identity's cache/outbox. Endpoint changes also invalidate cached server state rather than adopting it into the new deployment.
5. A handshake 404/405, redirect, malformed/unsupported response, or identity mismatch is a **setup/profile mismatch**, not an anonymous-mode signal. Keep data locked and show: **"This server is not a compatible authenticated backend for this account. Check the API endpoint and Clerk configuration."** Do not probe `/state`, send mutations, or drain an outbox to recover. 401 may use the existing single forced-refresh budget; then repeat admission for the same captured session before any data retry. A second 401 requires sign-in. 403 keeps required-session-task UI gated; 503/network failure keeps the gate closed with a retryable connection/setup message, not a successful login. Admission and data retries share the same bounded refresh budget, not recursively renewed budgets.

**Deployment invariant and limit:** auth-profile selection is explicit and fixed for the application deployment. Never auto-select a profile from credentials, a missing setting, health output, port discovery, or handshake failure. Do not mix authenticated and anonymous servers behind the same API origin or switch a live origin to the legacy profile between admission and data requests. Use a separately configured auth endpoint; a deliberate profile/endpoint change requires stopping/draining in-flight work and re-admission. A one-time handshake cannot detect an arbitrary same-origin server replacement or protect a mutation already sent to such a replacement; identity/generation checks are not server-profile attestation. Per-response owner headers would only reject the returned response, not undo a wrongly routed mutation, so they are not added in this minimal profile. Trusted endpoint transport and deployment isolation remain mandatory.

## 2. Verification policy

The server constructs an immutable principal only **after** signature and all claim checks succeed. Unverified parsing may select a bounded `kid` from an already trusted key set; it cannot select the issuer, URL, principal, or permissions.

| Field | Required auth-profile behavior |
|---|---|
| `alg` | Fixed server allowlist `RS256` only; reject `none`, HMAC/RSA confusion, and every other algorithm. Never take the allowlist from the token. |
| `kid` / signature | Nonempty bounded string; match one unambiguous RSA verification key in the configured instance's trusted JWKS and verify signature. Reject ambiguous duplicate IDs, unsuitable key types/usages/algorithms, invalid signatures, and unsupported critical JOSE extensions. |
| `iss` | Required nonempty string; **exact string equality** with configured `CLERK_ISSUER`. Do not normalize incoming claims or accept prefixes, subdomains, or another development/production instance. |
| `exp`, `nbf`, `iat` | All required integer Unix timestamps (not strings, booleans, NaN, or null). Verify expiry, not-before, and no future issuance, with at most 5 seconds of fixed clock leeway. Require `exp > iat` and `exp > nbf`. Clock leeway is not an offline-token grace period. |
| `sub`, `sid` | Required nonempty strings with bounded lengths; `sub` is ownership identity and `sid` is session context. Neither is a filesystem path. No substituted email or custom `userID`. |
| `v` | Require supported session-token version `2`; fail closed on other versions until reviewed. |
| `sts` | Permit absent or `"active"`; reject `"pending"`, other statuses, and malformed/null values. Successful cryptographic verification alone does not complete required session tasks. |
| `aud` | Default uncustomized-session mode: allow absence, but reject a present audience because no recipient was configured. If `CLERK_AUDIENCE` is set, require a well-formed string or nonempty string-array containing that exact server-configured recipient. Never infer it from bundle ID, API hostname, request, or token. Do not silently disable audience verification to accept an unfamiliar token. |
| `azp` | **Absent is allowed for native sessions.** If present, require a nonempty string in the exact server-configured `CLERK_AUTHORIZED_PARTIES` allowlist. Default empty allowlist means present values are rejected until explicitly configured. Null is not absence. Never require a browser origin on every native token or treat an arbitrary native bundle identifier as a verified origin. |

Clerk's default-claim reference does not promise an `aud`; its manual guide permits skipping `azp` validation when the claim is absent. An absent `azp` does not prove that a caller is a genuine app installation: these remain bearer credentials. In the default audience mode, the trust domain is the selected Clerk instance, not a cryptographically app-bound iOS binary. A shared-instance/multiple-resource deployment should explicitly configure an audience before release. A future browser/cookie integration needs a separate origin/CSRF review, not a relaxation of this native boundary.

No organization membership, client-editable metadata, or demo flag confers cross-user access. Impersonation/agent tokens carrying `act` are outside this initial profile and must be rejected rather than silently granting delegated access.

## 3. Trusted JWKS and failure behavior

- `CLERK_ISSUER` is trusted operator configuration: an exact HTTPS origin, without credentials, query, fragment, or path. The configured value must match the actual instance issuer. Derive `/.well-known/jwks.json` **only from this configuration**, never from incoming `iss`, `jku`, `jwk`, `x5u`, or discovery claims. Reject token-supplied alternate key-source headers; harmless extra headers such as Clerk's `oiat` need not be rejected.
- Verify TLS; disable redirects; use only the configured endpoint. Validate configuration at startup, including rejecting local/private/metadata destinations for deployed JWKS access. Apply an outbound destination policy appropriate to the host; HTTP-library scheme checks alone do not prevent SSRF. Never send a Clerk secret or a user bearer token to the public JWKS endpoint.
- Cache the **key set**, scoped by trusted issuer/URL, for at most 300 seconds. Do not enable an indefinite per-key cache. Select RSA signing keys only. Replace the set atomically after validation; do not mix keys between instances.
- On unknown `kid`, allow at most one refresh/relookup in that verification attempt, with a shared per-issuer single-flight refresh and 30-second cooldown. Use the same gate for a possible same-`kid` key replacement after signature failure; retry signature verification only once. Rate-bound failed fetches too, not just successful ones; a random-`kid` flood or issuer outage must not cause one external request per API request. A rotation during cooldown may briefly reject requests; never skip verification to compensate.
- Bound fetch time (5-second total deadline), response size (256 KiB), and key count (32). These are application policy choices, not promised Clerk defaults. Preserve an unexpired previously validated set after fetch failure; do not extend its TTL. Unknown keys never authenticate. No valid cached key and no successful refresh means fail closed.
- Missing/invalid auth configuration must prevent auth-profile startup (or keep protected handlers unavailable with 503); **never fall back to anonymous mode**. An explicit local anonymous profile may remain for old tests but must not be deployed as the auth service or share its user data root.
- Generic 401: absent/invalid/expired JWT or key definitively not found after permitted lookup. Return `WWW-Authenticate: Bearer` and an auth-profile error envelope with `code="unauthorized"`, `retryable=false`, no token/claims/vendor diagnostics. Verified-but-pending session returns generic 403 `session_pending`, `retryable=false`. JWKS/configuration infrastructure unavailable returns 503 `auth_unavailable`, `retryable=true`; it is not an instruction to sign in repeatedly. Existing error schemas/models will need an additive implementation change; none is made here.
- Offline verification does not instantly observe logout/revocation at Clerk. A previously minted, otherwise valid JWT may work until `exp` plus leeway. The client stops sending immediately on logout. Do not claim real-time revocation or add a secret-key-dependent introspection feature without an explicit requirement.

## 4. User ownership and minimal backend migration

**Ownership key:** `(verified iss, verified sub)`, mapped atomically to one internal opaque account ID with a database uniqueness constraint on `(issuer, subject)`. `sid` is not the storage key: signing in again must not create a different account. Path construction uses only the internal ID, never raw external input. Two issuers with the same `sub` are different principals.

The inspected backend has a singleton service/document, snapshot row `id=1`, receipts keyed by `(epoch, route, request_id)`, separate checkpoint database and Plaid vault files, and one housekeeping/daily coordinator. **Choose one isolated service/storage directory per user for the first migration**, rather than adding owner columns only to receipts while leaving all other singleton state shared. Preserve the existing snapshot/receipt transaction inside each directory. A row-based multitenant rewrite is deferred.

Every user owns their observations, ledger, feedback, preferences and consent, suppression settings, notification issuance history, processing runs, receipts, checkpoint threads/files, Plaid tokens/cursors/pending exchange/key material, and optional visit answers. Scope all mutable extension/coordinator/scheduler instances or mutable caches accordingly. Shared immutable rules and a credential-free verifier cache may remain shared.

Minimum internal interfaces (names describe the handoff, not existing implementation):

1. `authenticate_request(request) -> Principal(issuer, subject, session_id)` or typed auth failure; never returns a principal from decoded-but-unverified data.
2. `service_for(principal) -> UserServiceHandle(account_id, service)`; one synchronized initialization/start per account, safe close, no global current-user variable. Resolve only after authentication. The identity mapping is server-owned, not an account selector endpoint.
3. `UserWorkContext(account_id, data_epoch, generation)` accompanies every async synthesis, Plaid exchange/sync/recovery, housekeeping, scheduling, and ingestion task. Capture it before suspension and recheck before effects/commit; never resolve a late callback using whichever account is currently signed in. Cancellation alone is insufficient.
4. `delete_user_data(principal, original_mutation_body)` runs only within that account handle. Cancel/drain or fence its tasks, clear its vault/checkpoints/receipts/answers/notification and suppression state, advance its epoch, and preserve the existing deletion replay guarantees without resurrecting prior data. Other users remain unchanged. Deletion of app data is **not** deletion of the Clerk account.

Retain single-process/single-worker deployment initially: the current SQLite extension takes an exclusive file lock. Do not create/close a service per request or add Uvicorn workers without a cross-process ownership design. Enumerate server-owned user handles for scheduled work, never the last HTTP caller. Bound registry growth; idle eviction must not lose running tasks or required scheduled work.

**Legacy anonymous data:** leave it outside the authenticated root and never load/copy/attach it to the first login. Default new accounts start empty. Any later explicit migration requires a proven owner, operator authorization, backup/retention decisions, and a separate audited import; epoch equality or matching email is not proof.

## 5. Native client lifecycle

- Pin the verified Clerk iOS package; let the SDK own Keychain-backed authentication persistence. Obtain a fresh-enough token through SDK `getToken` per send; do not persist raw JWTs or implement refresh-token storage. A local JWT decode is never backend authentication or authorization.
- Hold a client identity context `(configured API base URL, configured issuer, SDK user ID, session ID, local auth generation)`. It selects a **local cache namespace only**; the server derives authority independently. Require SDK loaded state, an active (not merely non-null/pending) session, and successful `/auth/v1/session` admission for that captured context before sending data requests or loading/revealing user content.
- Namespace protected snapshots, outboxes, visit answers, notification IDs, consent UX, and any local processing state by identity. Include epoch within queued work; never reuse a legacy anonymous cache for a signed-in user. Same epoch/request IDs in two accounts must not cause data or receipt sharing.
- On logout or account switch, synchronously gate the UI and network first, increment the auth generation, cancel tasks/Link/HealthKit work, clear outgoing-account in-memory data, cached snapshots, pending outbox, optional answers and local reminders, and discard late callbacks. Then call SDK sign-out/set-active. Do not wait for a successful remote logout to hide data. A failed SDK logout stays locally locked; do not silently restore the old account on relaunch. Reauthentication/unlock must be deliberate.
- After a switch, await the new session/token, successfully re-admit through `/auth/v1/session`, then construct/open its account-scoped client and fetch `/state`. Never retry a prior user's mutation with the new user's token, even if request paths and epochs happen to match. Check identity/generation before and after each token fetch, network call, and response application.
- On 401, perform **at most one forced SDK refresh** for the same captured session, re-admit the same captured context through `/auth/v1/session`, then retry the exact original data request once. If the original request was admission itself, retry that handshake once instead; do not recurse or reset the refresh budget. The method/path/body bytes, `request_id`, and `data_epoch` remain unchanged; only authorization changes. Coalesce refreshes for concurrent requests. A second 401, no token, or authentication failure locks data and requests sign-in. Identity change cancels the retry. Do not refresh-loop on 403 pending or 503; ordinary bounded transport retries remain a separate budget.
- No expired-token fallback, local decode shortcut, or signed-out cache display. Network failures must not automatically masquerade as successful sign-in. SDK Keychain survival across app reinstalls is not a guarantee of valid/current server authorization.

## 6. Demo preload and release gates

Demo preload is a **later operator-only import of a separate JSON fixture**, explicitly bound to a chosen Clerk test-user `sub` and trusted issuer. Operator must confirm that exact test account in the intended instance; refuse omitted/ambiguous/unapproved targets. It must use the same user storage boundary and transaction/epoch protections. No client `is_demo`, arbitrary-user seed parameter, public demo route, automatic first-login fixture attachment, or privileged claim added to user-editable metadata. No fixture or importer is created by this handoff.

Required admission regressions (implementation tests, not claims of tests run here):

1. Point the Clerk-enabled frontend at the legacy anonymous backend, including the parent's reported existing loopback service on port 8000. `/auth/v1/session` returns 404: only admission may be attempted; assert **no `/state` or experience request, no mutation/outbox replay, no anonymous data displayed or cached**, and the explicit setup/profile mismatch message. A successful public health response does not change this outcome.
2. Capture SDK context B but supply token A and receive a valid A handshake. Assert exact subject mismatch prevents opening/loading/writing B's namespace, all data requests and mutations stay blocked, and the client never retags B's queued work as A. Repeat with an A-to-B switch while the handshake or a data response is in flight; stale results must be discarded.
3. Cover malformed/extra-field handshake JSON, wrong issuer/schema version, redirects/304, 401 refresh budget, pending 403, unavailable 503, and fresh admission after endpoint/session/generation changes. Test configuration rejects mixing anonymous/auth-profile deployments behind the selected origin; do not claim the handshake detects arbitrary server replacement.

Before release, prove: missing/bad credentials cause no domain side effects; wrong issuer/audience/signature/algorithm and missing time/sub/sid claims fail; native absent `azp` works but present-unlisted fails; pending sessions fail; JWKS rotation/outage/flood is bounded; two users with identical request IDs/epochs remain isolated; delete A leaves B byte-for-byte unchanged; A's late task cannot commit into B or a new epoch; logout/switch drops queued work; legacy anonymous data is never adopted; no demo or health data leak. Use scratch-generated test keys only, never provider private keys or published production signing material. The parent now reports configuration received and public JWKS HTTP 200 verified; this is not live-login or backend-authentication proof. Dashboard/native setup and live sign-in/device tests remain required.
